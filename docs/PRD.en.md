# Product Requirements Document (PRD) — XY Club Website Template

> Version: 1.4.3
> Status: Maintained
> Last updated: 2026-09
> Scope: This document is the **source of truth for requirements**; implementation details live in `ARCHITECTURE.md` / `API.md`, decisions in `docs/adr/`.

---

## 1. Product Positioning

**XY Club Website Template** is a reusable website template for clubs / communities:

- Liquid Glass visual style + micro-interactions
- Data-driven site (edit content, refresh, see it)
- Visual admin editor (usable by non-technical people)
- Pure static hosting supported (falls back to a snapshot when no Node process)

It is a **ready-to-use template**, not a custom site for one club — anyone can clone, edit content, and ship.

## 2. Target Users / Non-Goals

| Target Users | Non-Goals |
|--------------|-----------|
| Non-technical club organizers | Multi-user / role-based SaaS admin |
| Small teams wanting a good-looking site | High-traffic, multi-replica large sites |
| Individuals wanting zero-ops deploy | Platforms needing complex permissions / workflows |

## 3. Feature Modules

### 3.1 Site (data-driven render)
- 7 section types (field reference in `docs/SECTIONS.md`): services / members / events / news / gallery, etc.
- 4 themes (aurora / ocean / mist / sunset) via one CSS + variables
- 8 micro-interactions (`bind*`): cursor spotlight, card tilt, ripple, count-up, scroll progress, reveal, etc. — all respect `prefers-reduced-motion`, touch-degrade

### 3.2 Admin (visual editor)
- Login (single admin, scrypt hash — see ADR-001)
- Section CRUD, theme switch, site settings
- Image upload (allowlist jpg/png/webp/gif, ≤8MB, **no SVG**)
- Config export / import (export inlines data URIs; import restores real files)

### 3.3 Server (Node/Express)
- Static hosting of `public/`
- REST API: `GET /api/content`, `PUT /api/content`, `POST /api/login`, `POST /api/upload`, `GET /api/health`, etc. (see `docs/API.md`)
- Only runtime dependency `express`; password hashing via Node built-in `crypto`

### 3.4 Static fallback
- Without a Node process, the front-end falls back to `public/content.json` (generated by `scripts/build-static.js`, passwords stripped)
- Static mode: site fully usable, **admin unavailable**

## 4. Data Specification

Source of truth: `data/db.json`, shaped by `DEFAULT_DB` in `defaults.js`.

```json
{
  "settings": { "siteName": "...", "theme": "aurora", "adminPassword": "scrypt$..." },
  "sections": [ { "id": "s-game", "type": "services", "items": [] } ]
}
```

- Missing fields must have backward-compatible defaults (old data must not vanish)
- `adminPassword` is never stored in plaintext (scrypt hash)
- Field-source changes must sync `docs/SECTIONS.md` and `docs/API.md`

## 5. Non-Functional Requirements

| Dimension | Requirement |
|-----------|-------------|
| Zero-build / zero-dep | No front-end framework/bundler; runtime dep is only `express` |
| Single process | No multi-replica deploy (full JSON read/write conflicts) |
| Persistence | `data/` and `public/uploads/` on a persistent volume |
| Responsive | No breakage at 375px |
| Accessibility | Animations respect `prefers-reduced-motion` |
| Security | Escape user input before DOM; limit upload size; API auth explicitly required |
| Cross-version | `node >= 18` (CI matrix 18/20/22) |
