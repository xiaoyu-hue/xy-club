# 图片版权审查报告

> 审查日期：2026-10-01
> 审查范围：仓库内全部位图资源（`public/cases/images/`、`public/uploads/`）
> 审查触发：用户要求「审查此项目所有图片是否侵权」

---

## 一、结论摘要

| 类别 | 数量 | 是否实际展示 | 侵权风险评估 |
|------|------|-------------|-------------|
| 真实照片（案例配图） | 16 | **仅 4 张**（全在「临界摄影」案例） | ⚠️ **中风险**：许可主张无法自证 |
| 测试残留图片 | 2 | 否 | ✅ 已删除，无风险 |

**一句话结论**：目前**没有任何证据表明这些图片存在实际侵权**，但也**没有任何证据能证明它们的授权链完整**。
项目文档中「图片来自 Unsplash，保留授权台账」的承诺，**在当前仓库状态下无法被验证**——这是一处真实的合规隐患。

## 二、核心发现

### 发现 1：授权台账的 URL 格式不符合 Unsplash 规范（最关键）

`public/cases/CREDITS.md` 为 16 张图逐张登记了「原始页面」，格式为：

```
https://unsplash.com/photos/4d71bcdd2085
https://unsplash.com/photos/b67a49e012bf
```

问题是：**Unsplash 的照片 ID 是 11 位短码（[A-Za-z0-9_-]），不是 12 位十六进制。**

实测统计（脚本解析 `CREDITS.md`）：

```
台账中的 ID 总数: 16
长度分布: {12}          ← 全部 12 位
是否全为 hex: True      ← 全部由 0-9a-f 构成
样例: ['4d71bcdd2085', 'b67a49e012bf', '0c6688de566e', ...]
```

而 Unsplash 的真实格式是：

| 形态 | 格式 | 用途 | 示例 |
|------|------|------|------|
| 短 ID | 11 位字母数字（`varchar(11)`） | 网页地址 `unsplash.com/photos/<id>` | `9wYdW55NbnY`、`s6-TQxOxDSA`、`5S9_3fx1g8c` |
| 时间戳 ID | 13 位毫秒时间戳 + `-` + 12 位哈希 | CDN 图片地址 `images.unsplash.com/photo-<id>` | `photo-1517842645767-c639042777db` |

台账里的 `4d71bcdd2085` 是 **12 位纯 hex**——既不是 11 位短 ID，也不是时间戳形态。
**这意味着这些 URL 极可能是凭空生成的，点击后大概率 404，不能作为授权凭证。**

> 说明：我尝试直接访问 unsplash.com 做最终确认，但沙箱网络无法连通该域名（HTTP 000），
> 因此「URL 失效」这一条是**基于格式规范的强推断**，而非实测 404。这一点必须如实标注。

### 发现 2：图片文件本身没有任何溯源信息

对所有 16 个 `.webp` 做二进制与元数据扫描：

- **无 XMP**：不含 `<x:xmpmeta>`，没有创作者、来源、许可字段。
- **无 EXIF 溯源**：不含 `Make`/`Model`/`Artist`/`Photoshop` 等字段。
- **仅有的 Copyright 字符串是 ICC 色彩配置文件自带的自述**：
  `Copyright (c) 1998 Hewlett-Packard Company`、`Copyright 1999 Adobe Systems Incorporated`。
  这是「sRGB / Adobe RGB 色彩空间规范文档」的版权，**与照片作者无关**，不能倒推出图片出处。

结论：**图片与台账之间没有可校验的绑定关系**，台账改了也没人会发现。

### 发现 3：16 张图里只有 4 张真正被使用，其余 12 张是「僵尸文件」

逐张扫描 4 个案例 JSON 的图片引用（脚本递归遍历所有字段）：

| 案例 JSON | 图片引用 |
|-----------|---------|
| `cloudpivot.json`（叠云协作） | **无** |
| `mingli-law.json`（衡合律所） | **无** |
| `warmwood-coffee.json`（青坞咖啡） | **无** |
| `shiguang-photo.json`（临界摄影） | 4 张：`photo-work-1/2/3.webp` + `photo-hero.webp` |

引用计数：

```
coffee-*.webp        被引用 0 处   ← 僵尸
law-*.webp           被引用 0 处   ← 僵尸
saas-*.webp          被引用 0 处   ← 僵尸
photo-hero.webp      被引用 2 处   ← 在用
photo-work-1.webp    被引用 2 处   ← 在用
photo-work-2.webp    被引用 2 处   ← 在用
photo-work-3.webp    被引用 2 处   ← 在用
```

这带来两个直接后果：

1. **暴露面比想象中小**：线上真正展示的只有 4 张，风险敞口是 16 张的 1/4。
2. **仓库里有 12 张无主图片**：它们不参与任何页面渲染，但随仓库分发（GitHub Pages 是公开的），
   属于「没有用途、却带着不确定版权」的冗余资产。

### 发现 4：内容风险（肖像权/商标权）——原先的声明是错的

`CREDITS.md` 声称：

> 「本目录所有图片均为**无正脸人物、静物、建筑或风景题材**」
> 「已避免选择含可辨识品牌 Logo 的画面」

**逐张看图后，这个声明不成立：**

| 文件 | 实际内容 | 与声明是否相符 |
|------|---------|--------------|
| `saas-team.webp` | 开放办公室里**数十名可辨识人物**（含侧面、正脸） | ❌ **不符**，明显含人物 |
| `law-handshake.webp` | 两人握手特写（有肤色、手部、袖口细节） | ⚠️ 无正脸，但含人体 |
| `law-desk.webp` | 人物**手部**签字特写（无面部） | ⚠️ 部分相符 |
| `photo-hero.webp` | Zenit-E 相机 + 拍立得相纸，纸上有 **"PONY BROWN" 文字水印** | ⚠️ **含第三方商标/品牌字样** |
| `photo-work-1/2/3.webp` | 纯自然风光（雪山、云海、星空） | ✅ 相符 |
| `coffee-shop.webp` | 咖啡馆内景，含 **"BROEI"** 招牌、黑板菜单品牌名、**一名坐着的顾客** | ❌ **含第三方品牌 + 人物** |
| `coffee-hero/latte/beans.webp` | 静物（咖啡杯、咖啡豆） | ✅ 相符 |
| `law-hero.webp` | 正义女神雕像 | ✅ 相符 |
| `law-books.webp` | 图书馆书架与半身像 | ✅ 相符 |
| `saas-hero/dashboard/analytics.webp` | 地球夜景、仪表盘屏幕截图（虚构数据） | ✅ 相符（屏幕上的品牌名属虚构演示 UI） |

其中 **`saas-team.webp`（大量可辨识人物）** 是最需要注意的一张——
即便图片本身是免费授权的，**照片中人物的肖像权不随图片许可转移**，
用于商业宣传类场景时存在肖像权争议空间。

好消息：`saas-team.webp` 属于「僵尸文件」，**当前并未在任何页面展示**。
但 `coffee-shop.webp` 同理也是僵尸，`photo-hero.webp`（含 PONY BROWN 字样）**是在用的**。

### 发现 5：图片是真实摄影作品，不是 AI 生成

逐张目视检查（构图、景深、光比、纹理细节、镜头畸变）：全部符合真实摄影特征，**未发现 AI 生成痕迹**。

这一点反而加重了发现 1 的分量：如果是 AI 生成图，版权风险几乎为零；
但既然是真实照片，就**必然存在原作者**，也就必然需要一份能站得住脚的授权依据。

## 三、风险定级

| 风险项 | 等级 | 说明 |
|--------|------|------|
| 台账 URL 不可解析、无法自证授权 | 🟠 **中** | 项目对外宣称「已登记授权」，但登记内容不可验证，属**声明与事实不符** |
| `photo-hero.webp` 含 "PONY BROWN" 品牌字样且在用 | 🟠 **中** | 商标权不随 Unsplash License 转移 |
| `saas-team.webp` 含大量可辨识人物 | 🟡 低（当前） | 肖像权风险，但因是僵尸文件未展示，暂不暴露 |
| 12 张僵尸图片随仓库公开分发 | 🟡 低 | 无用途资产 + 不确定版权，建议清理 |
| 测试残留 PNG | ⚪ 无 | 已删除 |
| 图片为 AI 生成的误判风险 | ⚪ 无 | 已目视排除 |

**不存在「已确认侵权」的情形**——因为我没有找到这些图片的原始权利人，也就无从证明侵权。
但**同样无法证明合法**。在合规语境下，「无法证明」本身就是需要处理的问题。

## 四、修复建议（按优先级）

### 优先级 1：清理僵尸图片（零风险，立即可做）

12 张未被引用的图片（coffee-×4、law-×4、saas-×4）直接从仓库删除。
理由：
- 减少 12 份不确定版权资产的暴露；
- 仓库体积从约 930KB 降到约 250KB；
- 案例页面的「配图空缺」当前由 CSS 渐变占位，不影响视觉。

如果你希望保留（比如未来计划给这几个案例加图），那就必须先把它们的授权落实（见优先级 2）。

### 优先级 2：重建可信台账（推荐）

三条路径，按可靠性排序：

| 方案 | 做法 | 优点 | 代价 |
|------|------|------|------|
| **A. 换成自己拍/自己生成的图** | 用 AI 生图或实拍替换 4 张在用图 | 版权 100% 干净，无溯源负担 | 需要重新出图，风格需再调 |
| **B. 从可验证源重新下载** | 到 Unsplash/Pexels/Pixabay 重新挑图，**记录真实可点击的 URL**（Unsplash 11 位短码） | 保持摄影质感，成本低 | 需人工挑图 + 逐张验证链接可打开 |
| **C. 保留现状，仅勘误** | 只把台账里那 16 条假 URL 换成「来源不明，待补充」 | 最省事 | 不解决实质问题，合规隐患仍在 |

我倾向 **方案 A**：当前只有 4 张在用图，替换成本可控，且能一劳永逸地摆脱「授权链说不清」的状态。
若你更在意摄影质感，方案 B 也完全可行，关键动作是**每张图挑完后立刻点开 URL 确认能打开**，再写入台账。

### 优先级 3：加一道自动化闸门（防止再犯）

按项目现有「用测试守契约」的习惯（如 `tests/admin-perf.test.js`），新增一个
`tests/credits.test.js`，校验：

1. `CREDITS.md` 中每条 URL 能被正则匹配（Unsplash 11 位短码 / 或 Pexels/Pixabay 域名）；
2. `CREDITS.md` 里的文件清单与 `public/cases/images/` 实际文件**双向一致**（不多不少）；
3. 每个案例 JSON 引用的图片路径都真实存在。

这样「台账凭空捏造」和「僵尸图片」两类问题都会在 CI 阶段被拦下。

### 优先级 4：修正 `CREDITS.md` 与 README 的措辞

在授权落实之前，建议把对外文案从确定性表述改为可辩护的表述：

- 现状（`README.md` 第 80 行）：「图片来自 Unsplash（免费商用），来源与授权逐张登记在 CREDITS.md」
- 建议改为：「案例配图用于演示排版能力；图片授权信息见 `public/cases/CREDITS.md`，**该台账仍在核验中**」

避免在链接不可验证的情况下对外做出确定性授权承诺。
