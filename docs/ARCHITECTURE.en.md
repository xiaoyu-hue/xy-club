# Architecture

## In one sentence

A single Express process both serves static files and provides a REST API; all content lives in one JSON file; the front-end fetches data and renders it, with no build step.

## Data flow

```
                  ┌──────────────── Browser ────────────────┐
                  │                                        │
  site index.html ─┤  main.js                               │
                  │   └─ fetch /api/content ──────────┐    │
                  │      (fallback to ./content.json) │    │
                  │                                    │    │
  admin admin.html ─┤  admin.js                        │    │
                  │   └─ fetch /api/login → token ─┐   │    │
                  └────────────────────────────────┼───┼────┘
                                                   │   │
                  ┌────────── Node process ─────────┼───┼────┐
                  │  server.js                     ▼   ▼    │
                  │   ├─ static hosting public/             │
                  │   ├─ GET  /api/content  ────────────────┼──▶ read data/db.json
                  │   ├─ PUT  /api/content (auth) ──────────┼──▶ write data/db.json
                  │   ├─ POST /api/upload (auth) ──────────┼──▶ write public/uploads/
                  │   └─ session Map (in memory, 7-day TTL)│
                  │                                          │
                  │  data/db.json  ← generated from defaults.js on first start
                  └──────────────────────────────────────────┘
```

**Key point**: site and admin share the same `data/db.json`. What the admin changes is what the site shows on refresh — no cache layer, no rebuild.

## Storage

| File | Role | In repo? |
|------|------|----------|
| `data/db.json` | All content & settings (**contains plaintext admin password pre-hash**) | ❌ gitignored |
| `public/uploads/` | Images uploaded from admin | ❌ gitignored (`.gitkeep` kept) |
| `public/content.json` | Static snapshot, generated by `scripts/build-static.js` | ❌ build artifact |
| `data/db.json.corrupt-*` | Left on config parse failure for forensics | ❌ gitignored |

The shape of `db.json` is the shape of `DEFAULT_DB` in `defaults.js`:

```json
{
  "settings": { "siteName": "...", "theme": "aurora", "adminPassword": "..." },
  "sections": [ { "id": "s-game", "type": "services", "items": [] } ]
}
```

## Auth

1. Admin submits password → `POST /api/login`
2. Server verifies with **scrypt** (Node built-in `crypto`, no new dep), then issues a random token stored in an in-memory Map (7-day TTL)
3. Browser stores the token in `localStorage`
4. Subsequent writes carry the token; server compares

**Password storage**: `settings.adminPassword` looks like `scrypt$<salt>$<key>`. Legacy plaintext passwords from old versions are auto-upgraded to a hash on server start; a plaintext hit on login is also upgraded. To reset, use `node scripts/reset-password.js new-password` — never hand-edit plaintext.

**Rate limit**: same IP locked for 5 minutes after 5 wrong passwords (HTTP 429). Counter is in memory, cleared on restart.

**Known limits**: no CSRF protection; single password / single admin; session in memory (logout on restart). See README "Known limits".

## Theme mechanism

Themes are not multiple CSS files but **one CSS + 4 variable groups**:

```css
html[data-theme="aurora"] { --bg-a: ...; --ink: ...; --glass-1: ...; --accent: ...; }
html[data-theme="ocean"]  { ... }
html[data-theme="mist"]   { ... }   /* light */
html[data-theme="sunset"] { ... }
```

Switching a theme only changes one attribute: `<html data-theme>`. Every component references variables, never hard-codes colors — **this is a required convention when adding components**, or themes break.

## Micro-interactions

All in `main.js`, named `bind*`, registered in `init()`:

| Function | Role | Degrade |
|----------|------|---------|
| `bindSpotlight` | Cursor spotlight (updates `--mx` / `--my`) | Mouse devices only |
| `bindTilt` | Card 3D tilt | Mouse devices only |
| `bindRipple` | Button click ripple | — |
| `bindCountUp` | Hero number count-up | Respects `prefers-reduced-motion` |
| `bindScroll` | Progress bar + back-to-top + nav highlight | — |
| `bindReveal` | Staggered fade-in + background parallax | Respects `prefers-reduced-motion` |

## Static fallback (pure static hosting)

Environments like GitHub Pages have no Node process, so `/api/content` returns 404. The front-end then:

1. `fetch('/api/content')` fails or returns non-JSON
2. Falls back to `fetch('./content.json')` for the snapshot
3. Adds `static-mode` class to `<html>`; CSS hides the admin entry

Generate the snapshot:

```bash
node scripts/build-static.js    # writes public/content.json (password fields stripped)
```

> In static mode the site is fully usable; **admin is unavailable** (no server to write to).

## Image export / import

On config export, `/uploads/*` is **inlined as data URIs** so the JSON is self-contained; on import save, the server restores the data URI back to a real file under `uploads/`. Moving the config to another site won't break images, and `db.json` won't accumulate base64.

```
export (front-end admin.js)    save (server PUT /api/content)
  /uploads/a.png     ──▶      data:image/png;base64,...     ──▶   /uploads/<new>.png
```

Upload format allowlist: jpg / png / webp / gif. **SVG is not supported** — it can embed scripts and is rendered as a document by the browser on direct access.

## Constraints

- Zero front-end framework, zero build step
- Only runtime dependency: `express` (password hashing uses Node built-in `crypto`, no bcrypt)
- Single process: **do not deploy multiple replicas**; full JSON read/write will conflict
- `data/` and `public/uploads/` must sit on a persistent volume
