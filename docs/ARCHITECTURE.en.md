# Architecture Documentation

## One-liner

A single Express process serves both static files and REST APIs; all content lives in one JSON file; the frontend renders data with zero build steps.

---

## Data Flow

```
                  ┌──────────────── Browser ────────────────┐
                  │                                        │
  Official site index.html ─┤  main.js                     │
                  │   └─ fetch /api/content ──────────┐    │
                  │      (fallback to ./content.json) │    │
                  │                                    │    │
  Admin admin.html ─┤  admin.js                        │    │
                  │   └─ fetch /api/login → token ─┐   │    │
                  └────────────────────────────────┼───┼────┘
                                                   │   │
                  ┌────────── Node Process ─────────┼───┼────┐
                  │  server.js                     ▼   ▼    │
                  │   ├─ Static hosting public/            │
                  │   ├─ GET  /api/content  ────────────────┼──▶ Read data/db.json
                  │   ├─ PUT  /api/content (authenticated)──┼──▶ Write data/db.json
                  │   ├─ POST /api/upload (authenticated)───┼──▶ Write public/uploads/
                  │   └─ Session Map (in-memory, 7 days)     │
                  │                                            │
                  │  data/db.json ← generated from defaults.js on first start
                  └──────────────────────────────────────────┘
```

**Key point**: The official site and admin panel share the same `data/db.json`. Whatever the admin changes, the frontend reflects immediately—no cache layer, no rebuild.

## Storage

| File | Purpose | Git tracked? |
|------|---------|--------------|
| `data/db.json` | All content and settings (**contains admin password hash**) | ❌ gitignore |
| `public/uploads/` | Images uploaded via admin | ❌ gitignore (`.gitkeep` preserved) |
| `public/content.json` | Static snapshot, generated by `scripts/build-static.js` | ❌ build artifact |
| `data/db.json.corrupt-*` | Backup created when config parsing fails | ❌ gitignore |

The shape of `db.json` matches `DEFAULT_DB` in `defaults.js`:

```json
{
  "settings": { "siteName": "...", "theme": "aurora", "adminPassword": "..." },
  "sections": [ { "id": "s-game", "type": "services", "items": [] } ]
}
```

## Authentication

1. Admin submits password → `POST /api/login`
2. Server validates with **scrypt** (Node's built-in `crypto`, zero new dependencies), generates a random token stored in an in-memory Map (expires in 7 days)
3. Browser stores the token in `localStorage`
4. Subsequent write operations include the token for server-side verification

**Password storage**: `settings.adminPassword` looks like `scrypt$<salt>$<key>`.
Legacy plaintext passwords from older versions are **automatically upgraded** to hashes on server start; logging in with a plaintext password also triggers an upgrade.
If you forget the password, use `node scripts/reset-password.js <new-password>`—do not edit the plaintext directly.

**Rate limiting**: After 5 consecutive failed password attempts from the same IP, the IP is locked for 5 minutes (HTTP 429). Counter is in-memory, cleared on restart.

**CSRF protection**: Write operations (POST/PUT) add CSRF validation after authentication—the frontend fetches a token via `GET /api/csrf-token` after login, then includes it in the `x-csrf-token` header for every write request; tokens are bound to sessions and expire with them. Validation failures return HTTP 403. Login, `/api/csrf-token`, and `/api/health` endpoints are exempt.

**HTTP security headers**: A global response middleware adds `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, and `Content-Security-Policy` (whitelist for scripts/styles/images), and removes `X-Powered-By`.

**Input validation**: The request body for `PUT /api/content` first goes through `deepClone` (strips dangerous keys `__proto__` / `constructor` / `prototype` to prevent prototype pollution), then passes two whitelist checks—`ALLOWED_SETTINGS_KEYS` (settings fields) and `ALLOWED_SECTION_TYPES` (8 section types, must match `admin.js`'s `TYPES`), invalid input returns 400.

**Known limitations**: Single password, single admin; sessions are in-memory (logout on restart). See README's "Known Limitations" section.

## Theme System

Themes are not multiple CSS files—they're **one shared CSS + 8 variable sets** (synced with xy-intro-card):

```css
/* Dark themes (4 sets) */
html[data-theme="aurora"]   { --bg-a: ...; --ink: ...; --accent: #8b7cf6; }
html[data-theme="ocean"]    { --bg-a: ...; --ink: ...; --accent: #38bdf8; }
html[data-theme="sunset"]   { --bg-a: ...; --ink: ...; --accent: #fb7185; }

/* Light business themes (4 sets) */
html[data-theme="mist"]     { --bg-a: #eef1fb; --ink: #141a2e; --accent: #6d5df0; }
html[data-theme="neutral_morning"] { --bg-a: #f7f4f0; --ink: #1e2935; --accent: #5a6b7c; }
html[data-theme="neutral_cloud"]   { --bg-a: #f1f5f9; --ink: #0f172a; --accent: #4a5568; }
html[data-theme="neutral_oat"]     { --bg-a: #faf8f5; --ink: #2c2418; --accent: #6b5b4e; }
html[data-theme="neutral_navy"]    { --bg-a: #ffffff; --ink: #0f172a; --accent: #2c5282; }
```

| Category | Theme | Use Case |
|----------|-------|----------|
| Dark | aurora | Club classic |
| | ocean | Club tech style |
| | sunset | Club warm tone |
| Light | mist | Club clean style |
| | neutral_morning | General business |
| | neutral_cloud | Tech/consulting |
| | neutral_oat | Culture/catering |
| | neutral_navy | Finance/law |

Switching themes only changes one attribute on `<html data-theme>`. All components reference variables, never hardcode colors—**this is the convention you must follow when adding new components**, or switching themes will break.

## Static Fallback (for pure static hosting)

Environments like GitHub Pages have no Node process, so `/api/content` returns 404. In this case, the frontend:

1. `fetch('/api/content')` fails or returns non-JSON
2. Falls back to `fetch('./content.json')` to read the snapshot
3. Adds the `static-mode` class to `<html>`, CSS hides the admin entry automatically

Generate the snapshot:

```bash
node scripts/build-static.js    # Writes public/content.json (password field stripped)
```

> The official site works fully in static mode; **the admin panel is unavailable** (no server to write to).

## Image Export & Import

When exporting configuration, `/uploads/*` paths are **inlined as data URIs** to make the JSON self-contained; on import/save, the server restores data URIs back to real files under `uploads/`. This prevents broken images when moving configs between sites, while keeping `db.json` free of base64 bloat.

```
Export (frontend admin.js)         Save (server PUT /api/content)
  /uploads/a.png     ──▶      data:image/png;base64,...     ──▶   /uploads/<new>.png
```

Upload format whitelist: jpg / png / webp / gif. **SVG is not supported**—it can embed scripts and would be rendered as a document by the browser.

## Constraints

- Zero frontend framework, zero build steps
- Single runtime dependency: `express` (password hashing uses Node's built-in `crypto`, no bcrypt or similar)
- Single process: **do not deploy multiple replicas**—JSON full-read/write will conflict
- `data/` and `public/uploads/` must reside on persistent volumes
